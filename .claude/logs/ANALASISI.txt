Issue 1 — Response appears twice (workflow runs once)

This is a real system bug. The workflow executes once, but the reply is delivered to the chat twice, by two independent senders:





The AI Agent node auto-sends its answer to the chat UI. Live log at 14:57:39:

Code: execute-workflow.ts:6949-6957 — inside the AI Agent execution, chatServer.sendToSession(...).



The Chat Send node also sends the same answer. Code: chat-send.ts:145 — chatServer.sendToSession(...). It ran at 14:57:51.

So one execution → two deliveries, ~12s apart (AI Agent finishes → auto-send; then Chat Send finishes → send). That exactly matches your two bubbles ~14s apart.

Why it exists: the AI Agent has a built-in "auto-forward to chat" convenience (meant for workflows that have no Chat Send node). But your workflow does have a Chat Send node, so both fire and you get a duplicate. It's a design conflict between the agent's auto-send and the explicit Chat Send node.

Issue 2 — Memory isn't working

The AI Agent has no working conversation memory, and the attached "Memory" node is ignored. Two disconnected problems:





Memory is driven only by the agent's own memoryScope config — which is "none". agent-executor.ts:58: resolveMemoryScope(config.memoryScope). With none, agent-memory.ts:12 returns a null session key → loadAgentMemory returns [], appendAgentMemory does nothing → every turn is stateless (memory_written: false in every run).



The attached "Memory" sidecar node is never consulted. The agent reads the attached Chat Model node (agent-executor.ts:52 getAttachedNodeForHandle(..., 'chat_model')), but there is no equivalent call for 'memory'. And the Memory node's own description says it plainly: "Passthrough AI context node… it does not persist or search memory today." So attaching Memory does literally nothing.

So to answer your question directly: the agent doesn't "have" the lead details from memory — it only sees the current message. When you sent your name/phone/email, it echoed them back from that same message, not from remembered history. If you ask a follow-up in a new turn, it won't recall anything.

In n8n: attaching a Conversation Memory sub-node (Session ID + Context Window Length) is what enables memory — the agent loads the last N turns for that session and appends each exchange. Ours has the backend for this already (HybridMemoryService + loadAgentMemory/appendAgentMemory work) — it's just not wired to the attached Memory node, and the scope defaults to none.
