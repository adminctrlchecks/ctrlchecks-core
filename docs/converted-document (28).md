# CtrlChecks - Competitive Architecture Analysis

**Scope:** Compares only the components CtrlChecks actually has (verified in-repo, 2026‑08‑08) against the _equivalent_ component in n8n, Zapier, Make, Stack AI, and Pipedream. Not a full platform comparison - these are larger, more mature products; scale/integration-count claims are intentionally excluded.

**Method:** Repository inspection (worker/, ctrl_checks/) + live prod checks (GET /api/templates) for CtrlChecks facts. Web search of official docs for competitor facts. Every competitor claim is tagged **Confirmed** (stated in official docs found), **Observed** (seen in docs but not exhaustively verified), or **Not confirmed** (could not verify from available sources - never read as "they don't have this").

## 2\. Build-Time vs Runtime Values - the Core Comparison

This is the most architecturally distinctive part of CtrlChecks, so it gets its own section before the table.

### How CtrlChecks does it

Every input field on every node carries an explicit **fill mode** set at the registry level, not guessed per-workflow:

- manual_static - user must supply it; never auto-filled, even from upstream output.
- buildtime_ai_once - Gemini fills it once during workflow generation (a config value baked into the saved workflow JSON).
- runtime_ai - resolved **fresh on every execution**, from live upstream node output, at the moment the node runs.

A separate RuntimeInputSource audit trail (static_config | template | deterministic_runtime | runtime_ai | field_directive_ai | credential | system) records where each field's value actually came from on a given run, and runtime-field-contract.ts enforces hard rules on top of it - e.g., a field marked protected (credential-owned) can never be satisfied by runtime_ai, and a runtime_ai field can never be silently satisfied by leftover static_config. When no value is available, deterministic repair strategies (email extraction from lineage, title/body derivation, condition inference) run before the field is allowed to fail - AI is not the only fallback.

### How competitors do the equivalent

| **Platform**  | **Mechanism**                                                                                                                                                                                                                                              | **Build-time vs runtime**                                                                                                                                       | **Confidence**                                                                                                                        |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| **n8n**       | \$fromAI() function on tool parameters connected to an AI Agent node; the connected LLM fills the value **at the moment the tool is invoked**, using the field's declared "hint" (e.g. email) plus live context                                            | Runtime, but scoped to AI Agent **tool-calling parameters only** - not a property of arbitrary node fields outside the agent sub-graph                          | **Confirmed** (docs.n8n.io)                                                                                                           |
| **Zapier**    | AI Actions: an agent step can dynamically generate values for "the vast majority" of fields in a downstream action based on natural-language instructions; per-field control via setup params (provide value / "have AI guess" / exclude)                  | Runtime, generated per-run when the AI Action step executes; every AI-built Zap still requires human review before activation per Zapier's own docs             | **Confirmed** (docs.zapier.com/actions.zapier.com)                                                                                    |
| **Make**      | Manual field-to-field mapping (drag output of a prior module into a field) is the default and dominant mechanism; "AI Agents" scenarios (2025+) let an agent call a scenario as a tool with declared inputs/outputs, similar in shape to n8n's tool params | Mapping is build-time and static once wired; only the newer Agent-as-tool path is runtime-AI-driven, and is scoped to agent tool calls, not general node fields | **Confirmed** (help.make.com, developers.make.com) for mapping; agent-tool runtime behavior **Observed**, not exhaustively documented |
| **Stack AI**  | Node fields are configured in the visual builder; some nodes (e.g. Files Node) can be "exposed as input" so an end user supplies the value at runtime via the deployed app UI                                                                              | This is _user-supplied_ runtime input, not _AI-generated_ runtime input - distinct capability                                                                   | **Observed** (docs.stackai.com)                                                                                                       |
| **Pipedream** | Code-first: any step is a JS/Python/Go/Bash script, so a developer can call an LLM inside a step to compute a value at runtime - this is general-purpose code, not a declarative fill-mode on the field itself                                             | Runtime AI values are achievable but require the developer to write the logic each time; no schema-level fillMode concept                                       | **Not confirmed** - no evidence of a built-in declarative runtime-AI-field mechanism in official docs                                 |

### Verdict

CtrlChecks' distinguishing claim is **not** "we're the only platform where AI can fill a field at runtime" - n8n and Zapier both do this. The actual difference is **scope and enforcement**:

- n8n's and Make's runtime-AI value generation is confined to **AI Agent tool-calling parameters**; it does not apply to an arbitrary HTTP node's body field or a Sheets node's range unless that node is wired as an agent tool.
- Zapier's AI Actions apply more broadly (any action field) but the mechanism lives in a separate "AI Actions" product surface (Zapier Central/agents), not as a first-class attribute of the standard Zap-builder field.
- CtrlChecks declares fill mode **per field, in the registry, for every node type**, uniformly - a webhook's JSON body, a Sheets range, and a Slack message text all carry the same three-state contract, checked by the same enforcement layer regardless of whether the node sits behind an "agent."

This is a real architectural difference in **uniformity and enforcement**, not in the existence of the underlying capability. It should be described that way - not as "nobody else does this."

**Templates we should add:** industry-specific chains beyond current 4 categories (e.g., e-commerce/Shopify ops, DevOps/incident response, marketing/lead-gen sequences) - competitors' template libraries skew heavily toward these and CtrlChecks currently has none.

**Templates we should improve:** none currently show a live preview/outcome before import (n8n and Make both let users inspect the full node graph before committing).

**Template categories we are missing:** e-commerce, DevOps/CI, marketing automation, social media management - all large categories across every competitor researched.

**Structures worth learning from:** n8n's per-node inline documentation inside the template JSON itself (not just a top-level description) - CtrlChecks already does this via notes.why/notes.tips, which is a strength, not a gap.

**UX ideas worth adopting:** Zapier's "guided templates" pattern - let the user pick their two apps first, then the template assembles, rather than browsing a flat category list only.

## 5\. Strengths (repo + research supported)

1\. **Uniform, enforced field-fill contract across all node types**, not just AI-agent tool params - no competitor researched applies runtime-AI value generation this broadly by default (§2).

2\. **Fail-closed credential readiness gate** - verified fix (2026-07-29) closes a class of bug (silent execution with missing credentials) that public competitor docs don't describe guarding against explicitly.

3\. **Deterministic (non-AI) input completion** (input-guarantee.ts key-alias fallback) reduces reliance on the LLM for basic data-passing, unlike n8n where all node-to-node mapping is either manual or must go through an agent.

4\. **Single-source-of-truth registry** enforced by a build rule (.cursor/rules/permanent-core-architecture.mdc) - avoids the drift risk visible in, e.g., Make's per-app custom-component model where each integration owns its own field logic.

5\. **Templates carry inline per-node guidance** (notes.why/notes.tips) baked into the graph, not just a top-level description.

## 7\. Recommended Roadmap

**High priority**

- Make runtime_ai / buildtime_ai_once / manual_static visible per field in the Properties Panel (small, high trust payoff, no backend change - the data already exists in runtime-field-contract.ts audit output).
- Turn the existing AI Editor panel into a persistent chat surface for editing live workflows, not just build-time generation.

**Medium priority**

- Expand templates into e-commerce, DevOps, and marketing categories using the existing template + notes structure.
- Investigate and, if missing, add partial re-run/replay from a failed node.

**Low priority**

- Template graph preview before import.
- Optional "describe directly, skip wizard" path for returning users.

## 8\. Conclusion

1\. **Is the architecture aligned with modern AI automation platforms?** Yes - registry-driven node definitions, DAG-based execution, and a fill-mode contract for AI-vs-manual fields are patterns also present (in different shapes) in n8n and Zapier.

2\. **What's already comparable?** Credential vaulting/OAuth handling, DAG execution engine, trigger breadth for the providers CtrlChecks supports, and build-time AI configuration are all at functional parity with the equivalent competitor mechanisms.

3\. **What needs improvement?** Template library breadth, visibility of the runtime-AI mechanism in the UI, and a standing conversational AI surface for editing (not just generating) workflows.

4\. **Is the runtime field/value approach actually differentiated?** Partially. The _capability_ (AI generating a field value at execution time) exists in n8n and Zapier too. The _differentiation_ is that CtrlChecks applies it as a uniform, registry-enforced contract to every node field by default, with a fail-closed protected-field guard - competitors scope it to agent tool-calling or a separate "AI Actions" surface.

5\. **What to focus on next?** Make the existing runtime/build-time distinction visible and useful to users in the UI - the backend mechanism is ahead of what the UI currently exposes.

6\. **What to improve in templates?** Breadth (categories) and pre-import transparency (graph preview) - structure and inline guidance are already reasonable.

7\. **Architectural risks/assumptions to reconsider?** The wizard-first, hard-gated generation flow is a deliberate trade-off (guardrails vs flexibility) that should be revisited now that runtime-AI field resolution reduces the need for exhaustive upfront configuration - a lighter-weight generation path may now be viable without sacrificing the safety the wizard was built for.
