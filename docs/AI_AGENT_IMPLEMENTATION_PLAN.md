## Stage A — Core `ai_agent` backend node + shared types

**`worker/src/core/execution/agent/agent-types.ts`** *(CREATE)*
- Current: —
- Change: Define `AgentContext`, `AgentToolDescriptor`, `AgentMessage`, `AgentResult`, `RequireApprovalPolicy`, `ChatModelAdapter`, error `code` union, plus typed attachment graph metadata (`nodes`, `edges`, canonical handles).
- Why: Shared contracts for the whole module; no coupling to any node type.
- Dependencies: `unified-node-contract.ts` types, `ai-types.ts` (`WorkflowNode`).
- Risk: Low.
- Testing: Type-check only.

**`worker/src/core/registry/overrides/ai-agent.ts`** *(MODIFY)*
- Current: Wraps `ai_agent`, delegates to `executeViaLegacyExecutor` (single-shot LLM).
- Change: `execute()` → if **no `tool` edges attached**, keep the exact legacy delegate (D5). Else call new `runAgent(context)` from `agent-executor.ts`. Also override backend port metadata so `incomingPorts` includes `userInput`, legacy `input`, `chat_model`, `memory`, `tool`; `outgoingPorts` includes `success`, `error`, and legacy `output` as a success-compatible handle.
- Why: Revive the agent without breaking existing single-shot workflows.
- Dependencies: `agent-executor.ts`; a deliberate attachment graph source from `execute-workflow.ts` or workflow persistence. `NodeExecutionContext` does not currently type workflow edges, so do not assume edges are already in context.
- Risk: **Medium** — must preserve legacy output shape exactly.
- Testing: Unit: zero-tools path returns identical `{response_text, used_tools:[], …}`; with-tools path routes to `runAgent`; handle-registry test accepts `chat_model`/`memory`/`tool` and legacy `output`.

**`worker/src/services/nodes/node-library.ts`** *(MODIFY)*
- Current: `ai_agent` schema is single-shot LLM config with one default output schema generated by the registry.
- Change: Add agent-loop fields (`maxIterations`, `timeoutMs`, `maxToolResultChars`, `memoryScope`, `requireApprovalFor`) and output schema metadata for `success`/`error` while preserving the legacy default/output shape for zero-tools mode.
- Why: Backend catalog must match the revived node contract and frontend config.
- Dependencies: `overrides/ai-agent.ts`, Design §2/§9.
- Risk: Medium — schema drift can break validation or docs.
- Testing: Registry schema test for new fields and legacy defaults.

**`worker/src/api/execute-workflow.ts`** *(MODIFY)*
- Current: legacy `case 'ai_agent'` is at `6629`; AI-agent port input mapping reads `targetHandle` around `20107`; runtime planning currently treats all edges as execution dependencies.
- Change: Reconcile the legacy case with the registry override, pass or load a typed attachment graph for `ai_agent`, and filter `chat_model`/`memory`/`tool` attachment edges out of normal runtime execution order while keeping ordinary `userInput` edges in the DAG.
- Why: Manual tool attachments must be available to the agent without executing attached tool nodes before the agent.
- Dependencies: `agent-types.ts`, `agent-executor.ts`, existing workflow `{nodes, edges}` persistence.
- Risk: **High** — execution-order changes can affect saved workflows if filtering is too broad.
- Testing: Single-file runtime-plan test: attachment tool node is not pre-executed; `userInput` edge still orders normally; D5 legacy workflow still runs.

**`worker/src/core/utils/node-handle-registry.ts`** *(MODIFY)*
- Current: generated contracts come from registry ports, but target-handle normalization maps `chat_model`/`memory`/`tool` to `input` before checking whether those handles are valid.
- Change: Preserve valid `ai_agent` attachment handles before generic target mappings, or move target validity check before mappings in a way that does not regress existing aliases.
- Why: Backend validators/builders must not collapse attachment handles back to `input`.
- Dependencies: `overrides/ai-agent.ts` port metadata.
- Risk: Medium — shared handle utility used by AI builder/validators.
- Testing: Focused handle-registry test for `ai_agent` attachment handles plus existing `input`/`default` aliases.

## Stage B — Tool manifest (generic, zero hardcoding)

**`worker/src/core/execution/agent/tool-manifest.ts`** *(CREATE)*
- Current: —
- Change: `buildToolManifest(attachedNodes, registry)`: for each attached node, resolve type → `registry.get()`; apply **generic eligibility predicate** (exclude normalized `category==='trigger'`, raw `category==='triggers'`, `schema.internalOnly`, self); derive `parameters` JSON-schema from `getInputSchema()` (skip credential-owned/credential fields) + selected `operationContract` (required/forbidden/enum) + `aiSelectionCriteria` for name/description.
- Why: Any current/future node becomes a tool from registry metadata alone (§11c).
- Dependencies: `unified-node-registry.ts` accessors (verified present), `node-library` for `internalOnly`.
- Risk: Medium — schema derivation must be faithful across varied node shapes.
- Testing: Unit: manifest for a sample node matches its schema; **coverage test** (every eligible registry node included); **future-node test** (fake node → tool, no code edit); eligibility excludes a trigger + an `internalOnly` stub.

## Stage C — Tool-call loop

**`worker/src/core/execution/agent/agent-executor.ts`** *(CREATE)*
- Current: —
- Change: `runAgent(context)`: assemble `AgentContext`, build manifest (B), load memory (F), then loop: adapter.complete → final? emit Success : validate call → gate (L) → execute tool (D) → sanitize (L) → guardrails (L) → append → repeat. Explicit termination + structured Error.
- Why: The reasoning core; the only orchestrator.
- Dependencies: B, D, E, F, G-adapter, L.
- Risk: **High** — central logic; must be deterministic and bounded.
- Testing: Integration scenarios 1–10 (§ Stage M).

## Stage D — Existing executor integration (tool bridge)

**`worker/src/core/execution/agent/tool-adapter.ts`** *(CREATE)*
- Current: —
